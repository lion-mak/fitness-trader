# 拍照识别食物 · 可行性评估与实现路径

> 评估日期：2026-09-05 · 评估人：lion 🦁 · 结论：**做，但分三期，11 月上线只做前两期**

---

## 0. 结论先行

| 维度 | 判断 |
|---|---|
| 技术可行性 | ✅ 可行，且已有成熟中文菜品接口 |
| **精度** | ⚠️ **唯一的大风险**：不是"认不出菜"，而是"估不准量" |
| **成本** | ✅ 不是瓶颈，人均月成本在角级 |
| **工程/合规** | ⚠️ 需要一个服务端中转 + 隐私协议补充，这是真正的拦路虎 |

**核心建议：不要让 AI 直接把热量写进记录。** 让 AI 负责"给出候选 + 给默认值"，用户一键确认。这样识别误差只影响排序和初值，不污染账本——对一个以"数字准确"为卖点的产品来说，这条底线不能破。

---

## 1. 三条可选技术路径

### 路径 A：专用菜品识别 API（推荐先上）

代表：百度智能云「菜品识别」、腾讯云市场的食物热量识别接口。

- 百度菜品识别：覆盖 9000+ 菜品，单次返回 `name / probability / calorie（每 100g）/ 百科信息`；
  另有「自定义菜品识别」支持自建菜品图库、识别多菜品并返回位置坐标。
- 优点：便宜、结构化、中餐覆盖好、直接带每 100g 热量。
- 短板：
  - **只给每 100g 热量，不给份量** —— 份量得靠用户或另一条链路补；
  - 家常菜/混合餐置信度显著下降（官方 demo 里 top1 置信度 0.39 就是常态，不是异常）。

### 路径 B：通用视觉大模型（VLM）

代表：qwen-vl-max、GLM-4V、混元 Vision、豆包 Vision（均支持 JSON 结构化输出）。

- 优点：能理解"一盘西红柿炒蛋 + 半碗米饭"这类复合场景，能自己估重量，能一锅出多菜品。
- 缺点：比专用 API 贵一个量级；输出不稳定（需要用 JSON schema 约束 + 重试 + 兜底）；中文家常菜仍会翻车。

### 路径 C：混合（最终形态）

**VLM 出「菜名 + 份量 + 置信度」→ 用我们自己的 2052 条食物库做数值兜底。**

匹配到库里 → 用库里的每 100g 数据算（可控）；匹配不到 → 才用模型估值，并打上"估算"标记。
这样既享受 VLM 的理解力，又保证数值口径和全 App 一致。

## 2. 精度预期（要有心理准备）

| 环节 | 预期水平 |
|---|---|
| 菜品名识别（单菜品、常见菜） | top-1 约 70~90% |
| 菜品名识别（家常菜 / 混合餐 / 带汤汁） | 约 40~70% |
| **份量估算（无参照物）** | **MAPE 25~40%** ← 最大误差源 |
| 份量估算（有参照物：标准碗 / 硬币 / 筷子） | 15~25% |
| **端到端热量误差** | **±30~50% 是常态**，优化后最好 ±20% |

份量才是黑洞：一盘看起来差不多的炒饭，200g 和 350g 差 200 多 kcal，而隐性油脂（炒菜放了多少油）是纯视觉完全看不出来的。

**产品上的应对**：结果页强制显示"估算值 · 误差约 ±30%" + 显眼的"改成手填"入口；份量默认给中位值并做成滑杆，让用户 2 秒能改。

## 3. 调用成本

- **专用菜品 API**：按次计费，厘级单价（百度图像识别类常见为几百元/万次量级，以控制台当日报价为准）。
  按 3 次/天 × 30 天 = 90 次/月算，人均成本可忽略。
- **视觉大模型**：国内 VL 模型约 ¥1~10 / 百万 token。一张图约 1~2k input token + 200~400 output token
  → 约 **¥0.005~0.02 / 次**。90 次/月 ≈ **¥0.5~2 / 用户 / 月**；1000 DAU ≈ ¥500~2000/月。
  各家都有免费额度，自测阶段基本不花钱。

> 结论：**成本不是选型的决定因素，别为了省钱选差的模型。**

---

## 4. 工程与合规约束（真正的拦路虎）

1. **API Key 绝不能放前端 / 小程序包里** → 必须有服务端中转（云函数）。
   当前的 workbuddy.link 是纯静态托管，**挂不了服务端**，所以这一步必须先上云函数（微信云开发 / 腾讯云 SCF 均可）。
2. **用户照片属个人信息**：上传第三方前需要明确告知 + 授权，建议"用完即删、不落库"，隐私协议要补一条。
3. **小程序类目风险**：热量记录一般归「体育-健身」或「工具」，但文案一旦出现"健康建议 / 诊疗 / 疾病"就可能被判定为医疗健康类并索要资质。文案要回避诊断性表述。
4. **域名**：调用第三方接口需在小程序后台配 request 合法域名（已备案域名 + HTTPS）—— 正在办的 ICP 备案可复用。
5. **延迟**：VLM 的 p99 在 4~7s，必须做 loading 态和"识别失败请手选"的兜底，否则用户会以为卡死。

## 5. 推荐实现路径：三期

### P0（本周可做，不动架构）—— 拍照 = 留档 + 检索增强

- 拍照 → 存本地作为记录附件（视觉锚点，便于回溯）
- 同时弹出候选列表：来自 2052 条食物库 + 「我的常吃」+ 最近 7 天记录
- 用户点选 → 走现有份量页

**不引入任何外部 API、不需要服务端、零成本、零合规风险。**
收益：先验证"拍照"这个动作本身能不能提升记录率，再决定要不要为它花钱。

### P1（上线前 4 周）—— 接专用 API 做候选排序

- 云函数中转 → 百度菜品识别（top_num=5）
- 前端展示 5 个候选 + 置信度 → 用户点选 → **用我们库的每 100g 数据算热量**，份量仍由用户选

**AI 只影响"排序"，不影响"数值"** → 精度风险完全可控，成本可忽略，失败时降级到 P0 的手选。

### P2（上线后）—— VLM 直出「菜名 + 份量 + 热量」

- prompt 用 JSON schema 约束；拍照引导加参照物（"把筷子或硬币放在盘子旁边"）
- 结果页强制展示"估算 ±30%"与"改成手填"
- 只对 P1 验证后仍高频使用的用户放量

---

## 6. 我的建议与代价

- **建议：11 月上线只做 P0 + P1，P2 放到上线后。**
- 不做 P2 的代价：少一个"哇塞"的演示点，短视频传播素材弱一些。
- 做 P2 的代价：要多一个云函数 + 一份隐私合规 + 一条不可控的误差链路，**任何一个出问题都会卡住小程序审核**——而我们已经只剩约 9 周。
- 反面风险：如果竞品靠"拍照秒记"做增长，我们只有文字搜索会显得笨。**P1 是折中点**：拍照确实有用，数值仍在自己手里。
