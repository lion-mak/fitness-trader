## 一、审核期的能力边界（已查证）

| 动作 | 审核中能否做 | 依据 |
|---|---|---|
| 写代码 / 建项目 / 装云开发模板 | ✅ 可以 | 与备案完全无关 |
| 开通云开发环境、建云数据库集合 | ✅ 可以 | 不依赖备案 |
| **上传代码** | ✅ 可以 | — |
| **设为「体验版」+ 白名单真机扫码** | ✅ 可以 | 体验版免审核、限白名单 |
| **提交代码审核** | ❌ **不行** | 备案未完成会被官方拦截，控制台无法绕过 |
| **发布（点「发布」按钮）** | ❌ **不行** | 《互联网信息服务管理办法》 |
| 用普通二维码/小程序码访问 | ❌ 提示「未完成备案」 | 官方社区答复：属正常现象 |

⭐**结论**：审核期是一个**能开发、能真机测、只是不能上架**的窗口。它不是「等」，是**唯一能用来写代码的时间**。

## 三、还要不要在 PWA 上继续优化？（不要再改功能）

### 实测代码构成（`index.html` 5983 行）

| 部分 | 行数 | 占比 |
|---|---|---|
| HTML 结构 | 645 | 10.8% |
| CSS | 654 | 10.9% |
| JS · **纯计算逻辑** | **≈4100** | **68.5%（占 JS 的 88%）** |
| JS · DOM 操作（`document.` / `innerHTML` / `classList` …） | 443 | 7.4%（占 JS 9.5%） |
| JS · SVG 标签字符串拼接 | 127 | 2.1%（占 JS 2.7%） |

其他关键计数：`addEventListener` **44** 处 + `onclick` **21** 处 = **65 个交互接触点**；`innerHTML` **62** 处；
**`<canvas>` 元素 0 个**，`<svg>` 标签 **25** 个（其中 16 个是 24×24 静态图标，**9 个是动态数据图表**）。

### 结论：PWA 的 UI 层在小程序里 **0% 可复用**

三条硬约束（小程序视图层机制，非版本问题）：

1. **不解析 SVG** —— 小程序视图层只支持栅格图（PNG/JPG/WebP）。
   实测社区证据：`image` 塞 `data:image/svg+xml` 在 iOS 微信 8.0.45 可见、**Android 微信 8.0.52 不渲染**，
   且属**未文档化的私有行为**（不符《开发规范》第 4.2 条）。⇒ **SVG 路线不能作为线上方案。**
2. **没有 DOM** —— `document.*` 全失效，443 行 DOM 操作要改成 `setData()` + WXML 模板。
3. **没有 `innerHTML`** —— 62 处注入要改成 `wx:for` / `wx:if` 数据驱动。

⇒ 在 PWA 上打磨 UI = **同一件事写两遍**，且两边逻辑会分叉，日后维护成本翻倍。
⇒ 在 PWA 上加功能 = 小程序端必然要再实现一次。

### ⭐ 但有三件事例外（PWA 的新定位）

**PWA 已从「产品」降级为「数据采集器 + 设计稿」。** 它现阶段唯一不可替代的价值是**数据**：

- [x] **① 继续每天记录**。从现在到小程序上线还有 4~8 周，这些体重/饮食/运动记录是小程序上线后**唯一的冷启动数据**——没有它，小程序首屏是空的，用户体验等于从零开始。
- [x] **② 只修「记不了数据」的 bug**。记录断档不可恢复；纯视觉问题不用管。
- [x] **③ 不动 `state` 结构**。若必须改，同步 bump `SCHEMA_VERSION` 并补迁移步，否则数据迁移链（`__schema`）会在导入小程序时断掉。

**⇒ 不新增功能、不做视觉优化。UI 的活留到小程序里做（那里才是最终形态，且要重做一遍）。**

## 四、重写工作量分解

**复用率真相**（替换掉早期「整体 55~65%」的粗估）：

- ⭐ **纯计算逻辑 ≈ 88%（占 JS）→ 近乎直接可用**：`calcBMR` / `gapTier` / `paceWeeks` / `gapRankPct` /
  `exHeatBreaks` / `treemapLayout` / `klineGeom` / 经济体系 / 等级 / 抽卡概率 —— 都是无副作用的纯函数，
  **算法与公式 100% 保留**，只改「输入从哪来、输出给谁」。
- ⚠️ **渲染层 → 100% 重写**：9 个动态图表 + 65 个交互接触点 + 62 处 `innerHTML`。
- ⚠️ **数据层 → 换 API 不换结构**：`localStorage` → 云数据库；`state` 结构沿用 + 「粘贴 JSON 导入」接续历史。

### 按模块排（重写量降序）

| 模块 | 现有行数 | 改造方式 | 风险 |
|---|---|---|---|
| 分时图 `renderIntraday` | 250 | canvas 2d 手绘 + 触摸反查 | 中 |
| 持仓评级 `renderHoldingsRating` | 209 | 多为 DOM 布局 → WXML | 低 |
| 历史/K线 `renderHistoryChart`+`renderKline` | 117+113 | canvas 2d 手绘 | 中 |
| 运动热力网格 `renderExHeat` | 111 | canvas 2d，53×7 格 | 低 |
| 身体成分趋势 `renderBodyTrend` | 93 | canvas 2d | 低 |
| 账户总览 `renderAccount` | 89 | DOM → WXML（无图） | 低 |
| 净热量趋势 `renderTrend` | 84 | canvas 2d 柱图 | 低 |
| 缺口评级 `renderGapRating` | 58 | DOM → WXML（无图） | 低 |
| 大盘云图 `renderMarketMap` | 57 | canvas 2d（`treemapLayout` 照搬） | 中 |
| 3 个 tooltip 绑定 | ≈300 | 指针 X 反查索引的逻辑保留，输出改 canvas 重绘 | **中高** |
| 食物库 + 营养引擎 | 独立 `js/` 2 文件 | **≈95% 直接复用** | 低 |

⭐**tooltip 是隐藏难点**：现有实现用「指针 X 坐标 → 最近柱索引」（`klineGeom`），**不依赖元素命中**，
所以逻辑可整体保留；但在 canvas 上要自己实现「局部重绘」，比 DOM 版繁琐。

### 技术结论（已查证）

- ⭐ **图表一律用 `<canvas type="2d">` 手绘，不引 ECharts，不用 SVG data URI。**
  canvas 2d 比旧版 canvas 性能高 30~50%、内存少 20%，基础库 ≥2.9.0 全支持。
- ⚠️ canvas 2d 的 `drawImage` **只接受本地文件路径**，不接受网络矢量外链（要加载网络图得用 `canvas.createImage()`）。
- ⚠️ 高分屏要 `canvas.width = width * dpr` + `ctx.scale(dpr, dpr)`，否则发虚。
- **微信主包限 2 MB** —— v2.7.56 瘦身（4.14 MB → 283 KB）在此直接受益；食物库（768 KB）建议放云存储 + 版本号，改库免重提审。
